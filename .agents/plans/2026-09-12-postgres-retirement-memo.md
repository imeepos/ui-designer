# 决策备忘录：旧 rudder Postgres 库下线处置（待用户裁决）

> 状态：等待用户拍板。本备忘录只做决策支持，不执行任何处置。
> 背景：v0.1.0 后曾自建 Go server（用户/积分/计费），后端数据存 138 服务器 docker Postgres 实例（库名 `rudder`）。0.2.0 起客户端与生产全面切 cms，server 代码已删（git 历史可溯），该库自 D1 切换（2026-09-11 17:33）起无写入方。

## 选项

| 选项 | 动作 | 可逆性 | 资源占用 | 风险 |
|---|---|---|---|---|
| A 维持现状 | 不动（容器+库继续跑） | — | 138 上 docker 容器 + 盘空间持续占用 | 无数据风险；但无价值负载长期在线，易被遗忘 |
| B 快照后停用（建议） | `pg_dump` 全量导出存档（仓外冷备，如本机 ~/backups）→ `docker stop` 容器（**不删卷不删库**）→ 观察 30 天 → 清理 | 高：数据有快照，容器可随时 start | 仅快照文件（预计 <10MB） | 近乎零 |
| C 彻底清除 | 停用 + 删容器 + 删卷 | 不可逆（无快照则数据不可恢复；server 源码可从 git 重建但用户/积分数据永久丢失） | 零 | 误删无法挽回 |

## 影响面
- 该库仅服务已删除的 rudder-server，cms（现行生产）用独立 SQLite，与它零关联。
- 回滚场景：若用户要求「回到 v0.1.0 自建 server 体验」——需 git 重建 server + 该库数据。v0.1.0 用户量极小（发布仅一天即切 cms），实际回滚概率低。

## 建议
**选 B**。理由：成本一次约 10 分钟，保留完整回滚能力；30 天观察期后若无事即可升级为 C。选 A 是把不可逆决策无限期推迟；选 C 在无快照时放弃了一切回滚可能。

## 执行 runbook（若拍板 B，派发或人工执行均可）
1. `ssh root@43.240.223.138`（凭据用户侧持有）
2. `docker ps | grep postgres` 定位容器与卷
3. `docker exec <容器> pg_dump -U <user> -d rudder > /tmp/rudder-$(date +%F).sql` → `scp` 回本机 `~/backups/`
4. `sha256sum` 记录 → 本地验证 `pg_restore --list`（或 grep 建表语句）确认快照完整
5. `docker stop <容器>`（禁用 `rm`/`down -v`）
6. 账本记档：快照路径 + sha256 + 容器名；日历标注 30 天后复查清理
